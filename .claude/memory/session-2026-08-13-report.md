### 3. G5 unsaturated-window fix + попутный `cohens_d` баг

`detect_unsaturated_window()`: находит первый индекс, где `r_q(t)`
перестаёт строго расти (plateau onset), с минимумом 2 точки для fit.
Подключено в оба места (`cell_aggregation.reduce_g5`,
`phase_runner.run_phase`'s top-level G5).

Это вскрыло **третий, независимый баг**: `cohens_d` падал с
`ZeroDivisionError` при нулевой pooled-std (обе выборки без дисперсии) —
более узкое честное окно иногда даёт идентичный fit по всем сидам.
Исправлено: `d=0` для идентичных констант, `d=±inf` (со знаком) для
разных констант — математически корректная предельная семантика, не
костыль.

### 6. G1 — настоящий plateau-detector (`[A30]`)

`observables/spectral_dimension.py::detect_plateau()`: сканирует все
contiguous-окна `t_values`/`d_s(t)` (≥3 точки), окно — кандидат в plateau,
если `|slope линейной регрессии d_s vs log(t)| ≤ 0.1`; среди кандидатов
предпочтение — больше точек, затем шире log-t диапазон (tiebreak).
Возвращает `PlateauResult` с `d_s_hat`, `t_window`, `log_width`, `slope`,
`R²`, `converged` — весь диагностический набор, не голое число.

**Осознанно НЕ использован** R²-порог на плоском fit (предложение
внешнего анализа) — математически ненадёжен для истинно плоских данных
(`rvalue` у `scipy.stats.linregress` нестабилен при нулевом истинном
наклоне). Вместо этого — прямой порог на `|slope|`.

`t_values` расширен с 3 жёстко зашитых точек до 12-точечной log-сетки
`[0.1, 10.0]` (`run_smoke.py`) — с 3 точками детектор алгоритмически не
может работать (`min_points=3` заставляет использовать весь массив как
одно окно). Диапазон/плотность/порог — **provisional**, не
откалиброваны на реальных кривых Active (см. `[A30]`).

`CellObservableStatistics` получил новое поле `g1_converged_fraction` —
доля сидов, где plateau реально сошёлся (не молчаливый fallback).

5 hand-derived тестов, все численно перепроверены прототипом перед
записью assertions.

### 7. `[A9]` — сетка `(K, η)` заморожена, НЕ выполнена

```
K   ∈ {10, 25, 50, 100, 200}
η ∈ {0.02, 0.05, 0.1, 0.2, 0.4}
```

25 комбинаций, задокументировано ДО просмотра каких-либо результатов
(anti-fishing). **Оценка стоимости**: один прогон `development.yaml`
занял 71.5 минуты — 25 таких прогонов ≈ **30 часов**, нереалистично для
одной сессии и избыточно для robustness-проверки (которой достаточно
только Active/Frozen на одном маленьком N, не всех 7 arms на всех 5
размерах). Нужен отдельный, дешёвый sweep-конфиг — **не создан**, это
следующий шаг.

Правило принятия решения зафиксировано: ищем широкое плато стабильности,
не "удачный пиксель".

### 8. Correlation Shuffle — H0-контроль (`[A31]`)

`dynamics/adaptive.py::CorrelationShuffleAdaptation` — тот же
Oja-нормированный update, что у `HebbianAdaptation`, но off-diagonal
корреляции перемешаны по существующим рёбрам (`_shuffle_edge_correlations`,
свежая перестановка на каждый `update()`-вызов). Тестирует `H1`
("какая именно пара коррелирует — причинно важно") против `H0`
("достаточно любого reinforcement с тем же распределением величин").

**Реализована только как AdaptationRule** — НЕ подключена как 8-й
экспериментальный arm (нет записи в `Arm` enum, нет функции в
`arms_runner.py`, не участвует в G1-G6). Это осознанный scope cut,
задокументированный в `[A31]` — полное подключение требует отдельного
решения (входит ли в G6 15-cell matrix или остаётся отдельным отчётом)
и MCID-совместимого дизайна.

**Честная самокритика записана в `[A31]`**: перемешивание НА КАЖДОМ шаге
(а не один раз на весь прогон) может статистически "усреднить" любой
структурный эффект и сделать контроль неинформативным независимо от
истинности H0/H1 — нужно сравнить с вариантом с ОДНОЙ фиксированной
перестановкой на весь прогон, прежде чем доверять любому результату.

5 hand-derived тестов, все проходят.
